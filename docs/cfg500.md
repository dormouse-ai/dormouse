# cfg500 — 500M active / 20B stored from the real spec

Sizing only. Every count below comes from `StackSpec` + `assemble(..., device="meta").report()`
in `src/dormouse/model/spec.py` / `model/assemble.py`, the same call `dorm plan` makes.
There is no hand-derived substitute: the arithmetic shown here is a check on that call.

## Why the final shape

One bank is shared by all layers. Per expert:
`3·rank·(d + f) + 6·d + 12 = 3·2048·12288 + 24576 + 12 = 75,522,060`.
Bank stored = `261·per + E·d = 19,712,322,620`; bank active = `3·per + E·d = 227,631,140`.
Add `embed=32,768·4096`, `attn=138,203,488` and `norms=(2·16+1)·4096=135,168` to each.
`stored − active = (E − topk)·per = 258·75,522,060 ≈ 19.48e9`: almost all of the 20B is
inactive expert capacity, which is what makes 500M active possible at that stored size.

`n_layers=16` satisfies the hybrid 3:1 period; `d_ffn=8192` keeps the MoA GELU identity
(`3·d·f = 2·d·d_ffn_gelu`); `c_lat=512 ≤ d`; `topk=2 ≤ E`; `per/active=15% > 1%` floor.

## VRAM rough (analytic, not GPU-measured — CPU-only worktree)

Resident is the active set; the 19.7B bank's inactive experts must be offloaded to host RAM
(39.4 GB at bf16, ~3.9 GB at 1.58 bpw if `weight_qat="ternary"` is chosen).

| item | b2 | b4 |
|---|---:|---:|
| active weights, bf16 (500.2M × 2 B) | 0.93 GiB | 0.93 GiB |
| grads + Muon momentum, fp32 | 2.9 GiB | 2.9 GiB |
| fp16 NS transient (one grouped matrix region) | ≤0.2 GiB | ≤0.2 GiB |
| activations (≈1 GB per batch unit, project's b8 13.1 GiB peak) | ~2 GiB | ~4 GiB |
| **total** | **~6.0 GiB** | **~8.0 GiB** |
| plus 1,272 MiB pool headroom rule | ~7.2 GiB | ~9.2 GiB |

Fits a 15.9 GiB / 16 GB card. The activation term is an extrapolation from the measured
1B b8 peak (`docs/records/2026-11-16-step-graph-live-shape.md`), not a run at this shape;
confirm with `tools/preflight.py --batch 4` on a card before claiming a measured fit.

## Caveats / follow-ups

- `c_lat=512` at `d_model=4096` is a 12.5% bottleneck (demo was 18%); attention is 27.6%
  of active. Scaling `c_lat` with `d_model` needs a re-solve of `E` and is out of scope here.
- `rank=2048` is unmeasured in the economics table (recipe rank is 256); `dorm plan` prints
  `unmeasured` and never `take`. Treat the rank as a proposal until an A/B measures it.
- This branch has no `expert_device` field: a real `dorm train` would try to place all 20B
  on the card. An offload path is required before training, not just before planning.
- `weight_qat="none"` keeps stored at bf16; turning on ternary changes bytes, not counts.
